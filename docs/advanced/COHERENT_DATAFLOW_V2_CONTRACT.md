# NF003：一致的数据流V2契约与分步验收

## 当前实现边界

NF003从独立纯组件开始，不向现有`DataMovementModel.Kind`提前加入可运行但未接线的枚举。旧五个模型、`is*V1`判定、V1组级账本、旧研究参数和黄金结果保持原义。

本阶段A1新增[逻辑文件计划](<../../simulator/src/main/java/org/workflowsim/data/v2/DataflowFilePlan.java>)；它不是仿真模型开关，不会自动改变当前运行的来源、传输或副本目录。后续组件必须先独立通过验收，最后才开放完整的新模型/证据版本。

## A1：深冻结的逻辑文件与生产者索引

契约标记：`SCOPED_RESOLVED_WRITE_ONCE_FILES_V2`。

- 文件身份为`(workflowInputIndex, existingResolvedFileKey)`，不是FileItem对象身份、Job ID或实际持有副本的VM。
- 保留解析器已有文件键；不重复添加命名空间，也不通过拆分文件名猜测工作流。多输入解析器当前会产生`workflow-<index>/...`键。
- 一个逻辑文件至多有一个逻辑Task生产者；生产者必须是消费者的控制祖先，不限直接父节点。同Task原地读写和歧义多生产者拒绝，而不是当作外部SOURCE或猜一个父Job。
- 尺寸是当前解析结果中保留下来的有限、非负binary64字节数；同身份的所有保留描述必须完全一致，不设epsilon。零字节保持为有引用的零需求，不能变成“无输入”。
- **这不是原始输入声明检查器**：DAX解析器已经按first-wins合并的输入尺寸差异无法在此恢复。A1明确使用resolved-size语义，不宣称那些丢失的原始声明已经通过一致性检查；旧解析器不会被顺带收紧。
- 在聚类清空任务列表前捕获；复制逻辑ID、工作流归属、文件元数据和引用计数，不保留可变Task/FileItem。验证不调用会改变Task.depth的DAG深度分配器。
- `demandsFor(logicalTaskSubset)`按逻辑文件去重，但保留所有输入引用计数及消费Task集合。选择内生产者所产生的输入属于内部需求；重试可用原逻辑Task子集再次求需求，不遍历历史父Job输出列表。
- 引用字节数使用精确binary64输入BigDecimal乘以计数，允许大于Double.MAX_VALUE的合计；它不是实际传输的唯一载荷。
- 图验证和所需生产者祖先检查使用迭代遍历，不存储全对祖先矩阵。构建可能需要按消费者遍历祖先，活内存随图与文件/引用规模线性增长。

A1允许纯空计划/空Task选择；这不放宽现有仿真入口对合法工作流的要求。数据流运行初期仍计划保留静态目标绑定与已有的聚类支持边界，纯Task集合规范化不代表已实现新的聚类执行语义。

## 后续A2/A3：真实可见副本与同一个来源/路径决策

后续新版本将采用独立run-local状态，而不是给旧ReplicaCatalog站点字符串增加猜测含义。

1. 区分逻辑生产者与发布副本的Job尝试；只在实际完成后的成功Task输出发布点登记，位置来自实际Job VM，不读提交时预测的Task.finishTime。
2. 每个文件副本都有可见时刻。目标副本必须在该文件实际结算时才可见，不能等整个Job所有输入完成后一起冒充同时到达。
3. 选择规则初始采用：可见本地副本优先，否则最大独立路径瓶颈速率，稳定端点顺序打破平局。不使用瞬时队列做自适应路由。
4. 返回不可变的文件身份、载荷、所选副本来源/发布出处、目标、完整资源路径与独立速率上限；估时、准入、计费和证据使用**同一份决策**，不再按生产者重新构造另一条路径。
5. 物理路径资源缺失必须拒绝；明确不受限的SOURCE与找不到容量的链路是两种状态。不同VM即使同host也仍消耗端点资源；真正同VM本地引用才无网络服务。

## 最小运行生命周期策略

为避免把超出实现的能力混入声明，NF003最初选择以下明确策略：

- **释放**：`DEPENDENCY_READY_AT_OBSERVATION_V2`。工作流到达、当前控制依赖满足、目标VM固定后，在当前观察时刻选择来源并发起需求，不回溯父任务较早的完成时间。producer-eager预取需要独立发布通知与重试/到达门控，当前不冒称支持。
- **可见性**：`PER_FILE_SETTLEMENT_OBSERVATION_V2`。每个文件在内核处理其完成结算时可见；保留有效流体完成与实际观察时刻的区别，不从可选/截断trace推导运行正确性，不回溯修改目录。
- **合并**：同逻辑文件、同目标、重叠中的请求共用一次活动单播；保留不同Job尝试的等待者与引用观察。不同目标仍是不同传输。
- **计算门控**：只有全部所需文件在固定目标可见且控制依赖满足才能提交CPU；计算失败不表示缓存/VM丢失。失败Job中的成功Task输出不能被整体丢弃。
- **数值支持域**：后续选择/准入必须检查容量换算、独立速率、时延和绝对时刻可表示性；正有限输入本身不够。不能默许零进度事件循环，也不顺带修改旧求解器的已锁定行为。

## 新无争用对照

新对照保留相同的文件身份、释放/选择/可见性/去重规则及单流端点/链路上限，只取消跨流共享。不能替换成起点不同的旧pre-execution V1，也不能把物理容量全部移除。

机理测试使用同一组冻结来源/路径决策：两条100字节流共享10 B/s链路，独立服务各10秒，共享服务各20秒；单流和不共享链路的情况保持一致。完整DAG中缓存可见性随服务时刻变化，动态副本选择结果可能内生变化；未实现决策重放时，不宣称两次运行的路径历史完全固定或全DAG完成时间单调。

## 证据与接线门禁

V1的`V1_PARENT_OR_EXTERNAL_GROUP`、`MODELED_CONSTRAINED_SOURCE`和组级FCT不能被重新标为实际逐文件副本证明。新运行模型开放前，必须有独立版本的按文件/尝试/来源/路径/可见性证据，以及正确的配置重建、跨文件校验、rerun和显示路径；不只扩大V1允许列表。

SOURCE带宽与共享存储连接、必要输出上传属于NF004；受控在线VM分配属于NF005。TCP/ECN、复杂一致性协议、自适应路由和有限缓存淘汰仍不在本轮最小闭环内。

## 验收顺序

1. A1文件计划：手算重复引用、作用域、生产者祖先、原地/多写者反例、深图、解析/聚类/重试/会话清理边界。
2. A2副本状态：未发布/发布、失败/成功尝试、可见性时间、同目标等待者、零字节、本地与缓存保留。
3. A3来源/路径：V1反例的相反新契约、拓扑改变来源排序、稳定平局、不可变决策、容量/数字边界。
4. A4运行与新证据：逐文件完成、fanin、重试、晚观察/小传输、相同策略的无共享对照、旧五模型核心量不变。

A1当前验收：13项纯组件测试（含12000节点深链）与6项真实解析/聚类/重试边界测试通过；关联定向39项、完整Java/Javadoc1187项、Python30＋11项通过，旧五模型OFF重放仍全部IDENTICAL_CORE。初次集成测试调用了不存在的无参配置工厂，已只修正测试调用为现有重载，未扩大生产配置API。

每项先有测试，立即运行定向/集成门禁后再继续。旧[V1来源不一致测试](<../../simulator/src/test/java/org/workflowsim/NetworkEvidenceDatacenterTest.java>)应继续通过，不把更正新语义作为覆盖旧科学结果的理由。
