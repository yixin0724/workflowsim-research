# WorkflowSim 源码注释规范

## 目标与范围

本规范约束 WorkflowSim 当前维护源码的中文注释风格。目标是让研究者能够从源码中
确认模型假设、单位、算法决策、状态边界和失败语义，而不是为显而易见的赋值或循环
重复代码文字。

适用范围分为两个 Maven 模块：

- `simulator/src/main/java/org/workflowsim/**` 及其测试：稳定模拟器与通用研究 API；
- `experiments/src/main/java/org/workflowsim/**` 及其测试：历史示例、教程、reference 和特定研究驱动。

`simulator/src/main/java/org/cloudbus/**` 是随工程引入的 CloudSim 上游源码；不得为了本项目
中文化改写其版权、许可证、作者、上游出处或原有实现注释。任何文件已有的 Apache、GPL 或
其他法律/溯源头也必须原样保留。实验模块中的历史示例同样应尊重其原有来源说明；仅在
解释本项目模型边界、输入路径或测试 oracle 时补充中文注释。

## 语言与术语

- Java 包名、类型名、方法名、变量名、枚举常量、JSON 字段、manifest schema、错误消息和
  日志协议保持英文，避免破坏 API、测试与机器可读工件。
- 解释性 Javadoc 与行注释使用中文。首次出现的重要术语采用“中文（英文/缩写）”形式，
  例如“任务（Task）”“作业（Job）”“虚拟机（VM）”“主机（Host）”“最早完成时间
  （ECT）”和“百万条指令（MI）”。
- 论文原始标题、作者、URL、许可证文本与上游仓库名称保留原文；可在邻近的中文说明中
  解释其在本项目中的含义。

## Javadoc

- 每个包使用 `package-info.java` 说明职责、主要模型边界和不适用范围。
- 每个公开类型和重要内部类型应有以一句完整中文摘要开头的 Javadoc；类说明应优先解释
  职责、输入输出、状态所有权和研究边界。
- `simulator/` 的 Javadoc 重点说明稳定 API、单位和模型契约；`experiments/` 的 Javadoc
  重点说明教程/参考/研究身份、输入来源和不可推广范围。不要把特定研究的临时假设伪装成
  核心 API 的通用保证。
- public/protected 的 parser、builder、factory、runner、validator、算法入口、模型转换和
  有可观察副作用的方法，应使用中文 `@param`、`@return`、`@throws` 描述约束与结果。
- 不为名称已经清晰的简单 getter、setter、构造赋值和常量访问器重复编写模板化 Javadoc。
- 覆写方法在父类/接口契约已经足够时可使用 `{@inheritDoc}`；仅当本实现增加限制、排序
  规则或副作用时补充说明。

## 行级注释

行级注释只解释代码本身无法直接表达的原因，重点包括：

- 算法公式、单位换算、稳定 tie-break 与候选排序；
- 依赖图、状态机、全局状态重置和并发限制；
- 兼容历史 WorkflowSim 行为的原因；
- 失败处理、输入校验、证据工件完整性和统计解释边界；
- 测试中的非直观 fixture、数值 oracle 与回归场景。

不要为变量赋值、空值判断、循环索引、单行返回或显然的 API 调用添加重复说明。方法体内
不要使用 `/** ... */` 伪造 Javadoc；只有紧邻声明的 Javadoc 才会被标准 Javadoc 工具识别。

## 测试与验证

- 测试方法使用可搜索的行为式英文名称；对复杂模型输入、计算预期值和回归原因使用中文
  注释。
- 注释变更不得改变算法、随机性、输入校验、日志消息、JSON 字段或测试断言的运行语义。
- 只修改核心源码注释后至少运行 `mvn verify`；修改实验、示例或 P7/reference 注释/测试后
  运行 `mvn verify`。还应运行 `mvn -Pjavadoc verify` 生成并校验核心维护 API
  文档。
- v3 实验 manifest 分别记录核心组件和可选研究组件的源树身份。核心注释变化会改变核心
  组件 hash；P7/reference 注释变化会改变其研究组件 hash。需要与既有 P7 证据严格对应时，
  应在全部注释工作完成后重跑冻结矩阵、验证工件，再清理临时输出。源树 hash 是本地身份，
  不是 Git 提交或发行签名。
