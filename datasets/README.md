# Workflow Inputs and Datasets

This directory contains the classic Pegasus DAX, WfGen synthetic WfFormat JSON, and WfInstances WfFormat JSON derived from real executions. The latter two share the same JSON format, but their origins and evidence boundaries differ, and they must not be mixed into a single workload population.


## Choosing an Input

| Need | Choice | Usage boundary |
| --- | --- | --- |
| Start with the scientific workflows bundled in the repository | `dax/` classic inputs | Check the DAG, file naming, and size constraints against the selected model; the presence of a file does not mean every algorithm can use it |
| Use synthetic workflows or extend scale sweeps | `wfformat/` WfGen inputs | The standard checkout guarantees only a single Montage input; other recipes/scales must be prepared separately |
| Study graph structures derived from real executions | `wfinstances/v1.5/` | The standard checkout carries four small inputs; it is not a source-platform trace replay |

For run entry points see [Quick Start](<../docs/getting-started/QUICK_START.md>). In a Workbench configuration, `workflowPaths` is resolved relative to the directory containing the configuration file; Java examples, when run from the project root, use `datasets/...` paths. Research drivers that accept a dataset-root parameter use the path contract they explicitly prescribe; they do not guess the project location.

## Standard Checkout Scope

The repository ships **20 DAX inputs** for the five classic workflows, plus a separate [HEFT/CPOP paper example](<dax/heft/heft-paper-example.dax>) that is not counted among the 20.

The [ignore rules](<../.gitignore>) explicitly retain the following **1 WfFormat and 4 WfInstances** inputs:

```text
wfformat/montage/n100/montage-100-000.json
wfinstances/v1.5/makeflow/blast/blast-chameleon-small-001.json
wfinstances/v1.5/nextflow/bacass-dirt02-001.json
wfinstances/v1.5/pegasus/srasearch/srasearch-chameleon-10a-001.json
wfinstances/v1.5/pegasus/montage/montage-chameleon-2mass-005d-001.json
```

Parser cross-checks, the small end-to-end matrix, and CLI smoke tests depend on these JSON inputs; tests fail when a required file is missing. The default `mvn verify` validates both the core and experiments modules, but the small-input gate cannot be generalized into a certification of the entire upstream corpus.

The upstream file of [Epigenomics_997.dax](<dax/epigenomics/n997/Epigenomics_997.dax>) contained 209 negative file sizes and 57 negative job runtimes. The current version only removes the stray minus signs; the original unfixed version is preserved as [Epigenomics_997.dax.orig](<dax/epigenomics/n997/Epigenomics_997.dax.orig>) for source auditing, and the fix changed neither the DAG structure nor the absolute values of the numbers.

## Optional Full JSON Corpora

The full WfFormat/WfInstances corpora are not committed to the repository in full. The counts below describe the source scope covered by the local snapshots already on hand; they are not guaranteed to arrive with every clone, and they are not a certification of the entire corpus by the current simulations.

### WfGen Synthetic Inputs

The parsing records on hand for the full collection cover 42 synthetic instances, generated by an external Python project invoking WfCommons WfGen through `wfforge.data.wfgen_dataset`. Structures, runtimes, and file sizes come from learned distributions, not from raw observations of a production execution.

The set covers Montage, Epigenomics, BLAST, and 1000Genome at the 100/400/1000 scales, and Seismology at the 400/1000 scales. Before extending it, verify local files, indexes, generation parameters, and hashes; do not assume that every recipe comes with the same scales.

```text
datasets/wfformat/<recipe>/n<tasks>/<recipe>-<tasks>-<idx>.json
```

The full generated corpus may carry indexes and same-named `.manifest.json` files recording the recipe, the requested scales, the seeds, and the generation parameters; they are not the simulation-experiment manifests written by `ExperimentArtifactWriter`, their schemas must not be interchanged, and they are not guaranteed to ship with the standard checkout.

### WfInstances 1.5

Structure-validation records for the full snapshot on hand cover 180 JSON inputs, 118637 tasks, and 244573 edges: 30 Makeflow, 15 Nextflow, and 135 Pegasus. They only show that the corresponding snapshot parses and converts into DAGs; they do not show that every input passes the standard simulation pipeline.

```text
datasets/wfinstances/v1.5/<runtime-system>/<application>/<instance>.json
```

The parsers consume the task graph, the file sizes, and the runtimes; the source machines, core counts, memory, commands, timestamps, and observed makespan are not replayed automatically. Reports must state the input hashes and simulation parameters actually used; a real provenance alone does not justify claiming that algorithm performance was validated on a real production platform.

## Usage and Checking Commands

Run the repository's bundled inputs from the project root:

```bash
# WfGen 合成输入
mvn -pl :workflowsim-experiments -am compile exec:java \
  -Dexec.mainClass=org.workflowsim.examples.wfcommons.WfCommonsSimulationExample1 \
  -Dexec.args="datasets/wfformat/montage/n100/montage-100-000.json"

# WfInstances 真实执行派生输入
mvn -pl :workflowsim-experiments -am compile exec:java \
  -Dexec.mainClass=org.workflowsim.examples.wfcommons.WfCommonsSimulationExample1 \
  -Dexec.args="datasets/wfinstances/v1.5/makeflow/blast/blast-chameleon-small-001.json"

# 只检查传入目录实际存在的 JSON：解析/DAG 结构，不运行仿真
mvn -pl :workflowsim-experiments -am compile exec:java \
  -Dexec.mainClass=org.workflowsim.examples.wfcommons.WfCommonsJsonParserValidationExample \
  -Dexec.args="datasets/wfinstances/v1.5"
```

The last command fetches no missing corpora; check the reported counts against the list of files actually prepared instead of expecting the full-snapshot counts by default.

## Conversion, Compatibility, and Evidence

The main fields of the nested WfFormat 1.5 structure are listed below; the parser retains the declared version and does not automatically turn execution records into resource settings:

| Field | Conversion and checks |
|---|---|
| `schemaVersion` | the declared version reported for the input |
| `workflow.specification.tasks[].id/name` | internal Task identity and type |
| `parents` / `children` | dependencies must agree on both sides; missing endpoints, one-sided relations, and cycles are rejected |
| `inputFiles` / `outputFiles` | must reference declared files |
| `workflow.specification.files[].id/sizeInBytes` | file keys and finite non-negative byte sizes |
| `workflow.execution.tasks[].id/runtimeInSeconds` | every specification Task must carry a runtime |

The four WfInstances inputs shipped with the repository have fixed identities and hashes; their small end-to-end checks are maintained by the [input matrix definition](<../experiments/src/main/java/org/workflowsim/experiments/reference/p7/P7WfInstancesPilotMatrix.java>) and the [matrix test](<../experiments/src/test/java/org/workflowsim/experiments/reference/p7/P7WfInstancesPilotMatrixTest.java>); this is not a replay of the source-platform timeline.

Input runtimes are expressed in seconds and converted into model computation lengths by:

```text
max(100, floor(runtimeSeconds * runtimeReferenceMips * runtimeScale))
```

Defaults are `runtimeReferenceMips=1000.0` and `runtimeScale=1.0`. MI is the simulated amount of computation, not hardware-independent actual CPU usage. Explicit task-cost matrices are rounded into positive integer MI according to Task/VM seconds and the target MIPS; the raw normalized length is preserved as `lengthMi`, and the current attempt records `effectiveExecutionLengthMi`. The computed MI×PE×1,000,000 must be representable as a signed long; non-positive rounding results and overflow fail explicitly.

File sizes are finite non-negative byte equivalents, and the fluid model preserves representable fractional bytes. DAX forbids DOCTYPE/external entities; JSON parent-child relations must agree, and missing endpoints, one-sided dependencies, or cycles are rejected.

Duplicate INPUT sizes in DAX follow the first registered value and log a warning; this is not a guarantee that arbitrary models accept same-name conflicts. The LOCAL planner requires consistent file sizes; coherent file planning additionally requires decidable producers and control causality. An input with duplicated output names may be usable for plain online scheduling yet still fail these stricter models — see the [algorithm catalog](<../docs/algorithms/CATALOG.md>) and the [capability matrix](<../docs/advanced/DATAFLOW_CAPABILITY_MATRIX.md>).

Experiment manifests v4 record input hashes, arrival times, task-cost matrices, and platform declarations, with provenance in v3. Keep the original inputs and configurations; successful parsing, old evidence remaining readable, or passing field validation must not be interpreted as calibration to the source platform.

`wfforge.data.load_workflow` belongs to an external Python project and is not a runtime dependency of this Maven project; this project reads workflows directly through its Java parsers.
